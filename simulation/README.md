## ⛔ قبل أي شيء — شرطان لا تفاوض فيهما

**١) لا تشغّل هذا على الإنتاج. أبدًا.** ولا صفًّا واحدًا. أنشئ مشروع Supabase **منفصلًا** ونشرة Vercel **منفصلة**.

**٢) المشروع المنفصل يجب أن يكون على نفس خطة الإنتاج.**
هذا ليس تفصيلًا إداريًّا. البند الأوّل الذي نقيسه هو **تشبّع بركة PostgREST** — وحجم البركة وعدد الاتصالات وذاكرة القاعدة **كلّها تتبع الخطّة**. إن قِست على خطّةٍ مجّانيّة ثمّ أطلقت على خطّةٍ مدفوعة (أو العكس)، فالرقم الذي خرجتَ به **زينةٌ لا معنى لها** — وستظنّ نفسك آمنًا وأنت لست كذلك.

نفس الخطّة · نفس المنطقة (`fra1` للنشرة، وأوروبا للقاعدة) · نفس متغيّرات البيئة.

## الخطوات — بالترتيب

### ١. البيئة (مرّة واحدة، ~٢٠ دقيقة)

1. أنشئ مشروع Supabase جديدًا بنفس خطّة الإنتاج، في أوروبا.
2. من `Settings → API` انسخ: `URL`، `anon key`، `service_role key`.
3. طبّق كل الترحيلات من الصفر:
   ```bash
   supabase link --project-ref <المشروع-الجديد>
   supabase db push
   ```
4. **أثبت أن القاعدة سليمة قبل أي حمل** — الصقّ `supabase/tests/critical_checks.sql` في محرّر SQL:
   > يجب أن يكون **الفشل = ٠**. إن ظهر فشلٌ واحد، توقّف — المشكلة في البيئة لا في الحمل.
5. انشر نسخة preview على Vercel من نفس الفرع، بمتغيّرات المشروع الجديد، والمنطقة `fra1`.

### ٢. البذر (~٥ دقائق)

```bash
export SUPABASE_URL="https://<المشروع>.supabase.co"
export SUPABASE_SERVICE_KEY="<مفتاح الخدمة>"
export SUPABASE_ANON_KEY="<المفتاح العلنيّ>"
export TARGET_URL="https://<نشرة-preview>.vercel.app"
```

الصقّ `01_seed.sql` في محرّر SQL بالكامل، ثمّ:

```bash
node 02_make_sessions.mjs      # ينشئ ١٠٠ مالك + ٢٠٠ استقبال ويستخرج توكناتهم
```

يُخرج `sessions.json`. **لا ترفعه إلى git** — فيه توكنات صالحة.

### ٣. التشغيل (~٥٠ دقيقة، اتركه يعمل)

**طرفيّة ١ — الحمل:**
```bash
k6 run 03_load.js | tee results.txt
```

**طرفيّة ٢ — المتصفّحات (ابدأها بعد دقيقةٍ من k6):**
```bash
npx playwright install chromium      # مرّة واحدة فقط
node 06_browser.mjs | tee browser.txt
```

> ⚠ **`06_browser.mjs` يُشغَّل مع k6 — لا قبله ولا بعده.**
> خمس جلساتٍ في متصفّحٍ فارغ تقيس زمن الجلسة لا زمن النظام تحت الضغط. قيمتها كلّها في أنّها تمرّ بالمسارات نفسها **وk6 يضغط عليها في اللحظة نفسها**. شغّلها منفردةً وستحصل على أرقامٍ جميلةٍ لا تعني شيئًا.

يصعد k6 وحده: **١٠ ← ٢٥ ← ٥٠ ← ١٠٠ مطعم**، عشر دقائق لكل درجة، وتهدئةٌ دقيقتان بينها. و`06_browser.mjs` يوقّت نفسه على المراحل نفسها ويصنّف كل قياسٍ تحت درجته.

**ما تضيفه المتصفّحات ولا يقيسه k6:**
كتابات العميل تمرّ بـ**Server Actions** في Next.js، وهي التي تستهلك دالّة Vercel. `03_load.js` يقودها عبر RPC فيتخطّاها. الجلسات الخمس (٣ عملاء + ٢ استقبال) تمرّ بها فعلًا — فهي وحدها التي تقيس **سقف تزامن دوالّ Vercel**، وفيها **نقرةٌ مزدوجةٌ متعمَّدة على «جلوس»** لكشف ما إذا كان حارس التكرار في الواجهة وحدها.

**أثناء التشغيل** افتح محرّر SQL في تبويبٍ آخر والصقّ هذا كل بضع دقائق — هذا هو **البند رقم واحد**:

```sql
select count(*) filter (where state='active')  as نشِط,
       count(*) filter (where state='idle')    as خامل,
       count(*) filter (where wait_event_type='Client') as ينتظر,
       (select setting::int from pg_settings where name='max_connections') as السقف
from pg_stat_activity where usename='authenticator';
```

سجّل الرقم في الجدول أسفله عند كل درجة.

## 📱 تشغيلٌ من تابلت أندرويد (Honor Magic Pad وما شابهه) — ماذا يعمل فعلًا؟

سؤالٌ مشروع: لا PC، فقط تابلتٌ بمعالج Snapdragon. الجواب مختلفٌ لكل أداة:

**k6 — يعمل، بحيلةٍ غير رسميّة، ولا تثق به وحده.**
k6 مكتوبٌ بلغة Go الخالصة تقريبًا، وTermux يوفّر مترجم Go يبني لبيئته:
```bash
pkg install golang git
go install go.k6.io/k6@latest
~/go/bin/k6 version   # إن طبع رقم إصدارٍ، فقد نجح البناء
```
هذا **غير موثَّقٍ رسميًّا من Grafana** — لا حزمة k6 في مستودعات Termux، وما ورد هنا استنتاجٌ من طبيعة الأداة لا تجربةٌ مؤكَّدة. جرّبه بسكربتٍ تافهٍ أوّلًا (`k6 run --vus 1 --duration 5s script.js`) قبل أن تعتمد عليه للتشغيل الكامل.

**Playwright — لا تثق به على الجهاز. Chromium لا يعمل بثقةٍ تحت أندرويد.**
متصفّح Chromium الذي يُنزّله Playwright مبنيٌّ لِـglibc، وTermux بيئة Bionic (مكتبة أندرويد الأصليّة) — لا يعملان معًا مباشرةً. الطريق البديل (`proot-distro` لتشغيل توزيعة لينكسٍ كاملة داخل Termux) معروفٌ بمشاكل: الرمل الأمنيّ (sandbox) الذي يحتاجه Chromium يصطدم بقيود `ptrace` في proot، فيحتاج تعطيله (`--no-sandbox`) وهو أصلًا حلٌّ مجتمعيٌّ غير رسميّ لا ضمانة استقراره تحت حملٍ مستمرٍّ ٥٠ دقيقة. **لا تعتمد عليه لقياسٍ تبني عليه قرارًا.**

**البديل الموصى به: شغّله من مشغّل GitHub بدل جهازك — تبدأه من متصفّح التابلت نفسه.**
أضفنا `.github/workflows/simulation-load.yml`. خطواته:
1. من إعدادات مستودع GitHub (يفتح من متصفّح التابلت، بلا طرفيّة): `Settings → Secrets and variables → Actions` → أضف أربعة أسرار: `SIM_SUPABASE_URL`، `SIM_SUPABASE_ANON_KEY`، `SIM_SUPABASE_SERVICE_KEY`، `SIM_TARGET_URL` — كلّها لمشروع المحاكاة المنفصل، لا الإنتاج (المشغّل يرفض العمل إن أشارت إلى `ei8ht.app`).
2. تبويب `Actions` → **محاكاة ١٠٠ مطعم — حمل + متصفّحات** → `Run workflow` → اكتب «نعم» في حقل التأكيد.
3. k6 وPlaywright يعملان **في نفس المهمّة، على نفس الساعة** — التوازي مضمونٌ بالتصميم، لا بتوقيت يدويٍّ بين طرفيّتين. هذا في الواقع أوثق من تشغيلهما يدويًّا من جهازين.
4. النتائج (`results.txt`، `browser.txt`، `browser-results.json`) تُرفع كملفّاتٍ تُنزَّل من صفحة التشغيل — تفتحها من التابلت أيضًا.
5. `04_verify.sql` يبقى يدويًّا كما هو — الصقه في محرّر SQL بعد أن تقرأ النتائج.

> مشغّل GitHub المجّانيّ نفسه جهازٌ متواضع (نواتان، ٧ غيغا رام) — ليس "لا نهائيّ القدرة". لكنّه **معروفٌ وموثَّقٌ ومستقرّ**، بخلاف تابلتٍ يُخنَّق حراريًّا أو يُعلَّق تطبيقه في الخلفيّة دون سابق إنذار. إن أشبع هو نفسه عند الدرجة ١٠٠، فتلك حقيقةٌ عن أداة القياس تُذكَر في الجدول، لا خطأٌ يُخفى.

### إن أصررتَ على التشغيل من الجهاز مباشرةً (k6 فقط، لا Playwright)

- `termux-wake-lock` **قبل** البدء، وأوقف توفير الطاقة عن Termux من إعدادات النظام، وأبقِ الشاشة مضاءةً والجهاز على الشاحن — التشغيل الكامل ~٥٣ دقيقة متواصلة، وأندرويد يعلّق أي عمليةٍ خلفيّةٍ دون هذا.
- العدد الفعليّ للاتصالات المتزامنة معتدلٌ (كل VU ينام ١٠ث بين الطلبات) — هذا ليس عبء المعالجة الغالب على تابلتٍ حديث.
- **الخطر الحقيقيّ زمنيٌّ لا عدديّ**: الاختناق الحراريّ على جهازٍ بلا تبريدٍ نشِط يبدأ عادةً بعد ٢٠-٣٠ دقيقة تشغيلٍ متواصل — أي في مكانٍ ما بين الدرجة الثانية والثالثة (٢٥-٥٠ مطعمًا) إن لم تُفعِّل النقاط أعلاه، لا عند رقم مطاعم بعينه.
- **بلا Playwright يُشغَّل على الجهاز، فأنت تقيس القاعدة وPostgREST فقط — عمود "p95 مستخدم (متصفّح)" في الجدول يبقى فارغًا حتى تُشغّل المشغّل البديل.**

## 🔍 كيف تعرف أنّ العنق جهازك لا نظامك؟

الأرقام السيّئة قد تكذب عليك: قد تُظهر تباطؤًا وهو من التابلت لا من ei8ht.app. ثلاث علاماتٍ تفصل بينهما — اجمعها معًا، لا واحدةً بمفردها:

| العلامة | تُقاس من | يشير إلى: النظام هو العنق | يشير إلى: **جهازك** هو العنق |
|---|---|---|---|
| استهلاك معالج الجهاز | `top`/`htop` داخل Termux، أو إعدادات أندرويد ← البطاريّة ← استخدام التطبيقات | معتدلٌ (< ٧٠٪) وقت التباطؤ | قريبٌ من ١٠٠٪، أو إشعار "تسخين" من أندرويد |
| رمز ٥٠٤ | عمود `http_req_failed` في مخرجات k6، أو `mcp__Vercel__get_runtime_errors` | **صفر ٥٠٤** رغم البطء ← الخادم يستجيب، فالبطء ليس منه | ٥٠٤ فعليّة ← دالّة Vercel تجاوزت مهلتها، هذا عطبٌ حقيقيّ في النظام |
| بركة PostgREST | استعلام §٣ أعلاه (`pg_stat_activity`) | نشِط + خامل قريبان من السقف (٦٠) | نشِط + خامل بعيدان عن السقف رغم البطء الظاهر |

**القاعدة القاطعة**: إن رأيتَ الثلاثة معًا — معالجٌ محتقن، صفر ٥٠٤، وبركةٌ غير مشبَعة — فالبطء **من التابلت أو الشبكة بينك وفرانكفورت**، لا من دورٍ أو أنت. سجّل ذلك في الجدول كملاحظةٍ ("جهازٌ لا نظام") ولا تُدرجه ضمن نقاط الانكسار.

علامةٌ رابعة خاصّةٌ بـk6 نفسه: إن رأيت أخطاء مثل `dial tcp: i/o timeout` أو `context deadline exceeded` تصدر من **عمليّة k6 نفسها** (لا من رمز حالة HTTP)، فهذا التماس الشبكة/المعالج المحلّي فشل قبل أن يصل الطلب للخادم أصلًا — دليلٌ إضافيٌّ على أن العنق جهازيّ.

## الجدول الذي تملؤه

| الدرجة | طلبات/ث | معدّل الخطأ | p95 خادم (k6) | **p95 مستخدم (متصفّح)** | اتصالات نشطة | ٥٠٤؟ | **النتائج صحيحة؟** |
|---|---|---|---|---|---|---|---|
| ١٠ مطعمًا | | | | | | | |
| ٢٥ مطعمًا | | | | | | | |
| ٥٠ مطعمًا | | | | | | | |
| ١٠٠ مطعم | | | | | | | |

**العمودان معًا هما الفائدة.** الفارق بينهما طبيعيّ (تصيير + شبكة + رحلة بريدة↔فرانكفورت) لكنّه يجب أن يبقى **ثابتًا** بين الدرجات. فإن ثبت عمود k6 وانتفخ عمود المتصفّح مع التصعيد، فالاختناق **في طبقة Next.js لا في القاعدة** — أي سقف تزامن دوالّ Vercel، وهو البند الذي لم يكن يُقاس أصلًا.

**كيف تقرأه:**
- **معدّل الخطأ > ١٪** ← بداية التدهور.
- **أيّ `504`، أو خطأ > ٥٪** ← الفشل. سجّل الدرجة السابقة كسقفٍ آمن.
- **«النتائج صحيحة؟» = لا** ← توقّف فورًا مهما كانت السرعة. هذا أخطر من البطء.
- **اتصالات نشطة تقترب من السقف** ← البركة هي عنق الزجاجة، وهي البند الذي بُنيت المحاكاة لأجله.

## ما تتوقّعه (من قياسات القاعدة وحدها، ٧ أغسطس)

القاعدة خدمت ٣٠٠ صفٍّ في فرعٍ واحد بـ**٠٫٤٢ ms** للانضمام و**٠٫٣٧ ms** للإجلاس، ومنحنى مسطّحٍ حتى السقف. وأثقل مسارٍ (`tv_queue`) **٤٫٧ ms**.

فالقاعدة **ليست** ما سينكسر. المرشّحان: **بركة PostgREST** و**تزامن دوالّ Vercel** — ولهذا وُجدت هذه المحاكاة.

## ⚠ ما لن تكشفه هذه المحاكاة مهما نجحت

اكتبها على ورقةٍ بجانبك، فالنجاح هنا يُغري بالاطمئنان:

1. **أنّ موظّف الاستقبال لا يفهم الشاشة.** الروبوت يضغط الزرّ الصحيح دائمًا. الإنسان المرهق في ساعة الذروة لا.
2. **أنّ العميل يظنّ الزرّ شيئًا آخر** — يضغط «إلغاء» وهو يريد «تأكيد».
3. **أنّ شبكة المطعم ضعيفة.** المحاكاة تعمل على خطٍّ ممتاز؛ صالة المطعم فيها جدرانٌ وواي‑فاي مزدحم.
4. **أنّ الإشعار لا يصل** على جهازٍ قديم، أو على iOS بلا تثبيت التطبيق، أو والهاتف في وضع توفير الطاقة.
5. **أنّ الطابعة لا تطبع الباركود** بوضوح، أو أنّ الملصق وُضع في مكانٍ لا يراه أحد.
6. **أنّ المالك لا يفتح لوحته أصلًا** بعد الأسبوع الأول.
7. **أنّ الرقم صحيحٌ لكنّه بلا معنى** — «متوسط انتظار ١٢ دقيقة» قد يكون كذبةً إن كان نصف الناس يغادرون بلا إلغاء.

**هذه المحاكاة تجيب سؤالًا واحدًا: هل تتحمّل الآلة؟ ولا تجيب: هل ينجح المنتَج؟**
الثاني لا يُقاس إلا بمطعمٍ حقيقيٍّ لأسبوع.
